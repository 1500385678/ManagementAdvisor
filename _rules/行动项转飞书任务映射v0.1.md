## 一、设计原则

1. **4.1 行动项字段为入参契约**:本映射表的所有 4.1 侧字段名/数据类型/必填规则严格沿用 4.1 模板 §2.4,不另起炉灶改字段名
2. **飞书任务 API 为出参契约**:本映射表的飞书任务侧字段名/参数严格沿用 `lark-cli task +create` 命令签名(已验证 `--summary/--description/--due/--assignee/--follower/--tasklist-id/--data/--idempotency-key` 8 个核心参数),不允许"另起炉灶"调用非公开 API
3. **节点 4 说话人映射是责任人映射的前置**:4.1 责任人(姓名/花名)→ 飞书 `assignee`(open_id `ou_xxx`)必须走 4.2 §6.4 + 桥接 §二 节点 4 设计的 `directory.user.get` API,本映射表明确这一阻塞依赖
4. **强校验阻断**:沿用 4.1 §4.1 强校验规则——若行动项缺"责任人"或"截止时间",本映射表的 `--assignee` 与 `--due` 无法构造,**纪要不算结构化纪要,飞书任务不会自动创建**(节点 8 闭环触发条件)
5. **幂等键必带**:同一会议同一行动项多次创建飞书任务会产生重复任务,本映射表强制 `--idempotency-key = {meeting_id}-{action_item_id}` 避免重复(同一会议的行动项编号全局唯一,见 4.1 §2.4)
6. **降级显式化**:边界场景(责任人 open_id 缺失/截止时间"待确认"/任务清单不存在)沿用 4.2 §5.5 边界汇总矩阵风格,显式标注降级路径(创建/警告标签/仅记录不创建)
7. **可入库可复现**:每个映射条目标注"字段/类型/必填/默认值/转换规则",Phase 1 编码时按条目落库,便于 dogfood 阶段对账

## 二、4.1 行动项 8 字段 → 飞书任务字段映射表

> 4.1 §2.4 行动项 4 必填 + 2 可选 = 6 字段直接映射,新增 2 字段(幂等键/会议溯源)用于节点 8 闭环

### 2.1 核心映射(6 字段,1:1 映射)

| 4.1 行动项字段(§2.4) | 飞书任务字段(`lark-cli task +create`) | 映射类型 | 转换规则 | 强校验 |
|---|---|---|---|---|
| 行动项描述(string,必填) | `--summary`(string) | 直接 | 截断到 ≤ 100 字(飞书任务标题长度限制,超长部分进 `--description`) | 4.1 §4.1 模糊动词(看一下/研究一下/讨论一下)→ 拒绝创建 + 警告标签 |
| 责任人(string,必填,姓名/花名) | `--assignee`(open_id `ou_xxx`) | 间接 | 必须经 `directory.user.get` 翻译为 open_id(节点 4 说话人映射,见 §三 边界场景) | 缺责任人 → 拒绝创建 + 标"行动项 N 缺责任人" |
| 截止时间(ISO date `YYYY-MM-DD`,必填) | `--due`(string) | 直接 | 飞书 `--due` 支持 ISO 8601 / `YYYY-MM-DD` / 相对时间(`+2d`) / ms timestamp 4 种格式,本映射固定传 `YYYY-MM-DD` | 4.1 §4.1 "待确认" → 拒绝创建 + 标"行动项 N 截止时间待确认" |
| 优先级(enum P0/P1/P2,必填) | `--data.priority`(enum urgent/high/normal/low) | 间接 | P0 → urgent / P1 → high / P2 → normal(需走 `--data` JSON payload,见 §2.3) | 缺省 P1 → high |
| 状态(enum 待启动/进行中/已完成/阻塞,必填) | 不映射 | 不映射 | 飞书任务创建后默认"未完成"状态,4.1 状态流转在飞书任务侧由用户手动推进(不在创建时初始化) | 新建时 = "未完成" |
| 行动项编号(int,必填,会议内全局唯一) | `--idempotency-key`(string) | 间接 | 拼接为 `{meeting_id}-{action_item_id}`,同一行动项多次创建不会重复(飞书任务幂等键机制) | 必带,缺则可能被飞书侧去重为 1 个任务 |

### 2.2 扩展映射(2 可选字段)

| 4.1 行动项字段(§2.4) | 飞书任务字段 | 映射类型 | 转换规则 | 强校验 |
|---|---|---|---|---|
| 关联决策编号(int,可选) | `--description` 前置追加 | 文本 | 格式:`> 关联决策:决策 {decision_id} · {decision_content 截断到 50 字}\n\n`,便于飞书任务详情中反向溯源到会议纪要决策段 | 缺省 = 不追加 |
| 验收标准(string,可选) | `--description` 后置追加 | 文本 | 格式:`\n\n## 验收标准\n{acceptance}`,与行动项描述拼接为完整 Markdown | 缺省 = 不追加 |

### 2.3 JSON payload 完整样例(4.1 → 飞书 `--data`)

> `--data` 用于传入 `--summary/--description/--due/--assignee` 不直接支持的字段(如 `priority`),Phase 1 编码时 JSON 序列化后传入。

```json
{
  "summary": "输出 9 月迭代 PRD v2",
  "description": "> 关联决策:决策 1 · 9 月迭代仅做 3 个 P0 需求,2 个 P1 需求砍掉 1 个、顺延 1 个\n\n## 背景\n本次行动项源自会议 ID `mock-meeting-001` 行动项编号 1,见会议纪要段 4 行动项 1\n\n## 任务描述\nPRD v2 需含 3 个 P0 + 1 个 P1 需求范围\n\n## 验收标准\nPRD 通过技术评审 + 需求池入库",
  "due": "2026-09-11",
  "assignee": "ou_zhangsan",
  "priority": "urgent",
  "tasklist_id": "tlc_mock-product-sprint",
  "idempotency_key": "mock-meeting-001-1"
}
```

**字段来源说明**:
- `summary` ← 4.1 §2.4 行动项描述(截断到 100 字)
- `description` ← 4.1 行动项描述(超长部分) + 关联决策(若存在) + 验收标准(若存在) + 会议溯源(自动追加)
- `due` ← 4.1 截止时间(ISO date)
- `assignee` ← 4.1 责任人(姓名 → open_id,见 §三 边界场景)
- `priority` ← 4.1 优先级(P0 → urgent / P1 → high / P2 → normal)
- `tasklist_id` ← Phase 1 配置(按会议类别绑定,见 §四 任务清单归属)
- `idempotency_key` ← `{meeting_id}-{action_item_id}` 拼接(自动生成)

## 三、`lark-cli task +create` 调用样例

> v0.1 不调真机,以下示例为公开命令签名(`lark-cli task +create --help` 已验证 8 个核心参数),用于 Phase 1 编码时直接套用。

### 3.1 样例 1 · 周会行动项(P1 + 责任人 + 截止时间齐全)

```bash
lark-cli task +create \
  --as bot \
  --summary "同步本周 5 个需求池进展到产品群" \
  --description "## 背景\n本次行动项源自会议 mock-meeting-20260909-weekly-01 行动项编号 2\n\n## 任务描述\n- 拉取需求池 5 条 P0 进度\n- 整理为 1 页周报\n- 推送产品群\n\n## 验收标准\n- 周报推送成功 + 3 条 owner 已 @ 到位" \
  --due "2026-09-11" \
  --assignee "ou_ou_mock-product-zy" \
  --tasklist-id "tlc_mock-product-sprint" \
  --idempotency-key "mock-meeting-20260909-weekly-01-2" \
  --data '{"priority":"high"}'
```

```json
  "code": 0,
  "msg": "success",
  "data": {
    "task": {
      "task_id": "mock-task-001",
      "summary": "同步本周 5 个需求池进展到产品群",
      "description": "## 背景\n...",
      "due": "2026-09-11T00:00:00+08:00",
      "assignee": "ou_ou_mock-product-zy",
      "priority": "high",
      "tasklist_id": "tlc_mock-product-sprint",
```

### 3.2 样例 2 · 项目会行动项(P0 + 关联决策 + 验收标准)

```bash
lark-cli task +create \
  --as bot \
  --summary "技术方案文档:WebSocket + 长轮询降级架构" \
```

### 3.3 样例 3 · 月会行动项(P2 + 协助人 follower)

```bash
lark-cli task +create \
  --as bot \
  --summary "整理 9 月客户满意度调研报告" \
  --description "## 背景\n本次行动项源自会议 mock-meeting-20260909-monthly-01 行动项编号 8\n\n## 任务描述\n- 汇总 9 月 30 份 NPS 问卷\n- 与上月对比,识别下降维度\n- 输出 1 页报告给 CXO" \
  --due "2026-09-20" \
  --assignee "ou_ou_mock-cx-wm" \
  --follower "ou_ou_mock-cxo-zy" \
  --tasklist-id "tlc_mock-cx-monthly" \
  --idempotency-key "mock-meeting-20260909-monthly-01-8" \
  --data '{"priority":"normal"}'
```

**follower 字段说明**:`--follower` 用于"协助人/抄送"(飞书任务会通知但不强制 owner),适用于月度报告等需 CXO 知悉但不必 owner 的场景;不在 4.1 必填字段内,Phase 1 实施时按需启用。

## 四、任务清单归属(tasklist_id)与会议类别绑定

> 飞书任务必须归属于某个 tasklist,本映射表按 4.1 §三 3 类会议差异化字段,推荐默认任务清单映射(Phase 1 实施时按团队实际 tasklist ID 替换):

| 会议类别(4.1) | 推荐 tasklist | 命名规则 | 示例 ID |
|---|---|---|---|
| 周会 | 团队 Sprint 任务清单 | `tlc_<team>-sprint` | `tlc_product-sprint` |
| 月会 | 团队月度任务清单 | `tlc_<team>-monthly` | `tlc_cx-monthly` |
| 项目会 | 项目专用任务清单 | `tlc_<project>-<phase>` | `tlc_2026q3-iter01` |
| 1v1 | 个人 OKR 清单 | `tlc_<user>-okr` | `tlc_zhangsan-okr` |
| 临时会 | "会议纪要自动生成"通用清单 | `tlc_meeting-action-items` | `tlc_meeting-action-items` |

**降级策略**(沿用 4.2 §5.5 边界汇总矩阵风格):
- 若推荐 tasklist 不存在 → 降级到 `tlc_meeting-action-items` 通用清单 + 警告标签
- 若通用清单也不存在 → 拒绝创建任务 + 标"tasklist 缺失,需管理员手动创建" + 仍推送 Markdown 纪要到飞书群

## 五、强校验阻断规则(沿用 4.1 §4.1)

| 阻断条件 | 触发场景 | Phase 1 行为 | 飞书任务状态 |
|---|---|---|---|
| 行动项描述含模糊动词 | 4.1 §4.1 强校验 2:"看一下""研究一下""讨论一下" | 拒绝创建 + 警告标签"⚠️ 模糊动词,责任人 24h 内补充明确动作" | 不创建 |
| 责任人缺失或模糊 | 4.1 §4.1 强校验 1:责任人必须明确到人 | 拒绝创建 + 标"行动项 N 缺责任人,会议中请补全" | 不创建 |
| 截止时间为"待确认" | 4.1 §4.1 截止时间缺省处理 | 拒绝创建 + 标"行动项 N 截止时间待确认,会议后 24h 内补全" | 不创建 |
| 责任人 open_id 缺失 | 4.2 §6.4 说话人映射 API 未接通 / 用户不在飞书通讯录 | 警告标签"⚠️ 责任人 X 未找到 open_id,任务已创建但未指派" + 推送 Markdown 纪要补一段"行动项 N 待 owner 手动认领" | 创建,但 assignee 为空 |
| 任务清单不存在 | §四 降级策略 2 触发 | 拒绝创建 + 标"tasklist 缺失,管理员手动创建" + 仍推送 Markdown 纪要 | 不创建 |
| 幂等键冲突 | 同一会议同一行动项重复创建 | 飞书侧幂等机制,返回原 task_id 不创建新任务 | 不创建新任务 |

**纪要段 4 推送完整性兜底**:无论飞书任务创建成功/拒绝/警告,Markdown 纪要段 4 必须完整推送(节点 7 渲染输出);飞书任务创建失败/拒绝的情况,在 Markdown 段 4 末尾追加"⚠️ 飞书任务未闭环"汇总列表,便于管理员手动跟进。

## 六、真机凭证接入 checklist(6 步)

> Phase 1 启动时(预计 9/22 后),按本 checklist 推进 `lark-cli task +create` 真机凭证接入。本步骤与 4.2 §4 真机凭证 checklist 并行,**前置依赖**:4.2 §4 步骤 1-6 真机凭证接入完成(appId/appSecret + 4 个 API 权限)。

- [ ] **步骤 1 · 申请 task 权限**:在 4.2 §4 步骤 2 申请的 4 个权限基础上,**追加申请** `task:task:write`(飞书任务写权限)→ 提交审核(预计 1-2 工作日)
- [ ] **步骤 2 · 创建 tasklist**:在飞书目标团队下创建 3 类默认 tasklist:`<团队>-sprint`(周会用) / `<团队>-monthly`(月会用) / `<团队>-<项目代号>-<阶段>`(项目会用)→ 记录 tasklist_id 到 Phase 1 配置(替代 §四 占位 `tlc_mock-*`)
- [ ] **步骤 3 · 获取 appId/appSecret**:沿用 4.2 §4 步骤 3 的 appId/appSecret(同 app,无需重复申请)→ 配置到 `lark-cli --profile <profile>`
- [ ] **步骤 4 · 单元 dry-run**:用 `lark-cli task +create --dry-run --data '{...}'` 验证 JSON payload 构造无误(无真机调用,仅打印请求)→ 覆盖 3.1/3.2/3.3 三个样例
- [ ] **步骤 5 · 真机创建测试任务**:在测试会议(`mock-meeting-test-001`)中提取 1 个行动项,真机创建飞书任务 → 验证 `--idempotency-key` 防重复生效(同一会议同一行动项创建 2 次,应返回同一 task_id)
- [ ] **步骤 6 · 闭环验证**:从会议 ID `mock-meeting-test-001` → 提取行动项 → 映射 → 创建任务 → 在飞书任务详情页验证:summary/description/due/assignee/priority/tasklist_id 6 字段全部正确 → 记录到测试日志

**预计总耗时**:1-2 工作日(步骤 1 权限审核 1-2 天 + 步骤 2-6 实施 0.5 天,与 4.2 §4 真机凭证并行不阻塞)

**风险点**:
- 飞书任务权限审核可能要求"应用已上线 7 天后才能申请 task:task:write"——若遇此情况,降级方案:Phase 1 上线先用 Markdown 纪要段 4 推送 + 行动项 owner 手动创建任务,飞书任务自动闭环推迟到应用上线 7 天后
- 同一 app 申请 task 权限可能与 4.2 §4 步骤 2 的 4 个权限审批合并,实际耗时可能更短

## 七、边界场景预研(5 维度)

> Phase 1 实施时按本节预研结果做边界处理,沿用 4.2 §5.5 边界汇总矩阵风格。

### 7.1 边界 1 · 责任人 open_id 映射失败

| 场景 | 概率 | 触发条件 | Phase 1 行为 |
|---|---|---|---|
| 责任人姓名与飞书通讯录一致 | 90% | 4.2 §6.4 `directory.user.get` API 通,姓名精确匹配 | 创建任务,正常 assignee |
| 责任人姓名/花名差异 | 8% | 4.1 写"老张",飞书通讯录"张三" | 模糊匹配,若唯一候选 → 创建任务 + 警告标签"⚠️ 姓名模糊匹配,已映射为 张三" |
| 责任人不在飞书通讯录 | 1.5% | 外部嘉宾/已离职员工 | 警告标签"⚠️ 责任人 X 未找到 open_id,任务已创建但未指派" + 推送 Markdown 纪要补"行动项 N 待 owner 手动认领" |
| 责任人重名(2+ 候选) | 0.5% | 飞书通讯录有 2 个"张三" | 拒绝创建 + 标"行动项 N 责任人重名,会议中请明确" |

### 7.2 边界 2 · 截止时间解析失败

| 场景 | 概率 | 触发条件 | Phase 1 行为 |
|---|---|---|---|
| 标准 ISO date | 85% | 4.1 输出 `YYYY-MM-DD` 格式 | 直接传 `--due` |
| 口语化日期 | 12% | 4.1 抽取"下周三" → LLM 标准化失败 | 拒绝创建 + 标"行动项 N 截止时间待确认(原话:下周三)" |
| 模糊截止 | 2.5% | 4.1 写"尽快""本月内" | 拒绝创建 + 标"行动项 N 截止时间待确认" |
| 已过期 | 0.5% | 4.1 输出 < 当前日期(会议追溯场景) | 创建任务但加警告标签"⚠️ 截止时间已过期,请 owner 重新评估" |

### 7.3 边界 3 · 优先级与飞书优先级体系差异

| 4.1 优先级 | 飞书 `--data.priority` | 备注 |
|---|---|---|
| P0(阻塞性) | `urgent` | 飞书最高优先级,红色标记 |
| P1(重要) | `high` | 飞书次高优先级,橙色标记 |
| P2(普通) | `normal` | 飞书普通优先级,蓝色标记 |
| (4.1 缺省 P1) | `high` | 同 P1 |

**注意**:飞书任务优先级体系(`urgent/high/normal/low`)与 4.1 优先级(`P0/P1/P2`)为 1:1 映射,不存在"4.1 P2 → 飞书 low"的情况——4.1 P2 = 飞书 normal,飞书 low 在 4.1 体系内无对应(若需"低优先级"语义,扩展 4.1 模板增加 P3 字段,留 Phase 2)。

### 7.4 边界 4 · 任务清单归属

| 场景 | 触发条件 | Phase 1 行为 |
|---|---|---|
| 推荐 tasklist 存在 | §四 绑定表命中 | 正常创建 |
| 推荐 tasklist 不存在 | 团队未配置该 tasklist | 降级到 `tlc_meeting-action-items` + 警告标签 |
| 通用 tasklist 也不存在 | Phase 1 实施初期未创建 | 拒绝创建 + 标"tasklist 缺失,管理员手动创建" |
| tasklist 已归档/删除 | 团队组织调整 | 同上 |

### 7.5 边界 5 · 行动项描述长度

| 场景 | 触发条件 | Phase 1 行为 |
|---|---|---|
| 描述 ≤ 100 字 | 4.1 标准输出 | 全部进 `--summary` |
| 描述 100-500 字 | 4.1 含详细背景 | 100 字内进 `--summary`,超出部分进 `--description` 前缀 |
| 描述 > 500 字 | 4.1 异常输出(可能含转写原文) | 截断到 500 字 + 警告标签"⚠️ 行动项描述过长,已截断" |
| 描述含 Markdown 表格 | 4.1 表格化输出 | 完整保留(飞书任务 `--description` 支持 Markdown) |

### 7.6 边界汇总矩阵(沿用 4.2 §5.5 风格)

| 行动项类型 | 飞书任务创建 | 推送形式 | 备注 |
|---|---|---|---|
| 4 字段齐全 + open_id 命中 + tasklist 存在 | ✅ 创建 | 完整飞书任务 + Markdown 纪要段 4 | 默认 |
| 4 字段齐全 + open_id 缺失 | ⚠️ 创建但未指派 | 飞书任务(空 assignee) + Markdown 纪要 + 警告标签 | 边界 1 |
| 4 字段齐全 + 截止时间口语化 | ❌ 拒绝创建 | 仅 Markdown 纪要 + 警告标签 | 边界 2 |
| 缺责任人 | ❌ 拒绝创建 | 仅 Markdown 纪要 + 警告标签 | §五 强校验 |
| 缺截止时间 | ❌ 拒绝创建 | 仅 Markdown 纪要 + 警告标签 | §五 强校验 |
| 模糊动词 | ❌ 拒绝创建 | 仅 Markdown 纪要 + 警告标签 | §五 强校验 |
| tasklist 不存在 | ⚠️ 降级通用清单 | 飞书任务(通用 tasklist) + Markdown 纪要 + 警告标签 | 边界 4 |

**降级兜底话术**(沿用 `_templates/飞书bot指令识别设计v0.1` §三 兜底话术 3 条):
- 全部成功:"本次会议纪要已生成,N 条行动项已转飞书任务,见任务列表"
- 部分失败:"已生成 5 段式纪要,N 条行动项已转飞书任务,M 条因 [原因] 未闭环,详见纪要末尾汇总"
- 全部失败:"本次会议行动项转飞书任务失败,原因:[原因],已通知管理员,会议 ID: <meeting_id>"

## 九、不做什么

- **不写代码**:本映射表是字段映射 + 调用样例 + 边界预研,所有代码化工作留到 Phase 1 启动后 T3 后端按 §八 checklist 推进
- **不调 `lark-cli task +create` 真机**:依赖 `lark-cli task +create --help` 公开命令签名 + 飞书任务 API 公开响应 schema,真机验证留到 §六 步骤 5
- **不定义新的优先级体系**:本映射表沿用 4.1 P0/P1/P2 → 飞书 urgent/high/normal 1:1 映射,不允许"扩展 P3"等自定义语义(留 Phase 2)
- **不涉及任务状态机**:4.1 行动项状态(待启动/进行中/已完成/阻塞)的流转由飞书任务用户手动推进,不初始化;状态同步/反向回流到会议纪要库是 Phase 2 升级项
- **不替代 4.1/4.2/桥接/prompt 样例**:本映射表是端到端资产链第 5 块,与前 4 块合并构成 Phase 1 第 1 项完整前置资产,单独使用无法闭环
